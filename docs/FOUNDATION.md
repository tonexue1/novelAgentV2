# 理论基础：受控递推（项目心智模型）

> 本文固化项目的第一性原理。所有架构决策（分层存储、分桶检索、软失效、
> 分层规划、卷边界复盘）都是这套心智模型的推论。

---

## 0. 一句话

本项目 = **上下文工程 + 记忆工程**：把一个会漂移、会爆炸、会丢长程依赖的朴素递推
`s(i) = f(s(i-1))`，改造成"**有界上下文 + 结构化多尺度记忆 + 全局规划锚 + 外部寻址**"的
**受控递推**。$R$ 和 $U$ 是全部难点，$f$（LLM）只是执行器。

---

## 1. 剧本生成的本质是一个递推

剧本天然是状态依赖的：后一章基于前面状态生成。朴素形式：

```
s(i) = f(s(i-1))
```

但这是"影子"。真实形态是一个**耦合系统**：

```
x_i = f( R(S_{i-1}, P, i) )     ← 生成：只看检索出的有界切片
S_i = U(S_{i-1}, x_i)           ← 记忆：结构化更新
```

符号：
- `x_i`：第 i 章**剧本**（输出）
- `S_i`：第 i 章后的**完整叙事状态**（世界/人物/走向的全量真相，**会无限增长**）
- `c_i = R(...)`：真正喂进 LLM 的**上下文窗口**（必须有界）
- `P`：全局规划（L0/L1，慢变的**控制信号 / 锚**）
- `f`：生成（LLM）；`R`：检索/上下文构造；`U`：记忆更新

**核心洞察**：递推真正发生在 `S` 上，但 `S` 太大不能直接进 `f`。所有工程量都在 `R` 和 `U`：

- **上下文工程 = 设计 R**：从大状态里选出**有界且够用**的切片。
- **记忆工程 = 设计 U 和 S 的表示**：把历史压成**结构化、可寻址、能演化**的紧状态。

`f`（LLM）反而是最不需要操心的部分。

---

## 2. 朴素递推撑不过 200 步的三种崩法

若天真地让 `s(i-1)` = 前一章原文（或全历史）：

| 崩法 | 数学表现 | 解药（对应架构机制） |
|------|---------|--------------------|
| **状态爆炸** | 全历史 \|S\|=O(i)，第 200 章塞不进窗口 | U 把 S 压成**结构化+去重+软失效**，R 只取 top-k → \|c_i\|=O(1) |
| **漂移/误差累积** | f 有损且随机，微小偏差逐章复利，200 步后跑成另一个故事 | **控制信号 P** 当锚（打破纯马尔可夫）+ 一致性闸做**误差投影**，拉回合法流形 |
| **长程依赖丢失** | 第 12 章→第 160 章的伏笔，**根本不在 s(i-1) 里** | 显式**可寻址外部记忆**（伏笔台账、as-of 检索、出处回指） |

---

## 3. 伏笔 = 长程依赖 = 一阶递推的结构性缺陷

`s(i)=f(s(i-1))` 是**一阶递推**，只能携带"上一步"。但小说存在**跨百章依赖**：

```
x_160 依赖 x_12   （护道印伏笔）
```

这个依赖不可能经 s_13…s_159 无损传递（类比 RNN 梯度消失：信息逐步被稀释/覆盖）。

**这是记忆系统存在的全部理由**：它给递推加了**外部可寻址记忆 + 跳连（skip connection）**，
本质就是 RNN → Attention 那一步——**让 x_160 直接"寻址"到 x_12，不依赖链式传递。**

> 结论：我们做的不是一阶递推，而是**带外部记忆和全局注意力的受控递推**。

---

## 4. 状态 S 是"多时间尺度"分量的叠加

`S_i` 不是单一状态，而是几个**变化速率不同**的分量，各自需要不同的 R 和 U：

| 状态分量 | 时间尺度 | U（更新策略） | R（检索策略） | 对应 Store |
|---------|---------|--------------|--------------|-----------|
| 世界设定 canon | 慢（近静态） | 极少变，版本化 | 几乎常驻上下文 | WorldStore |
| 人物状态（三观/性格/语气/能力） | 中 | 软失效 + 章节戳 | as-of 快照 | MemoryStore |
| 走向/伏笔 | 中 | 状态机推进（ADVANCE/FULFILL/PLANT） | 精确过滤（非向量） | ArcStore |
| 场景连续性 | 快 | 章内滚动摘要 | 最近 N 场 | (运行态)+ScriptStore |

朴素递推的错误 = **把所有分量当成一个 s 一锅炖**。真实系统必须**按尺度分离**：
慢的常驻、中的检索、快的滚动。→ 这就是为什么要分四个 Store：**它们是 S 的四个分量，各有各的 U/R。**

---

## 5. 完整公式

```
x_i = f( R(S_{i-1}, P, i) )          ← 生成：只看检索出的有界切片
S_i = U(S_{i-1}, x_i)                ← 记忆：结构化更新，分尺度
P   = 全局规划(慢变控制信号)          ← 防漂移的锚（L0/L1，滚动细化 L2/L3）
S   = [world, character, arc, scene] ← 状态是多尺度分量
外部记忆寻址处理长程依赖(伏笔)         ← 打破一阶链式的信息瓶颈
```

---

## 5.5 创作层 ⇄ 记忆层：锚在 Script 的闭环

R 和 U 不是两个独立步骤，而是一个**闭环的两支**：创作层的上下文是记忆层的**投影**(R)，
创作层的产出又**反作用**回记忆层(U)。

```
        ┌──────────── R (出库投影) ────────────┐
        ▼                                       │
   [记忆/Arc]                              [Context c_i]
   派生投影                                     │
        ▲                                       ▼
        └── U/抽取 (入库投影) ── [Script spine] ◀── f 产出 x_i
                                 主真相·冻结·只追加
```

**闭环锚在 Script spine 上，不悬空。** 若只是"记忆喂创作、创作改记忆"两者互指，错误会在环里滚雪球。
关键是有一个**唯一不动点**：Script 既是 `f` 的产物、又是 U 投影的源、又是 R 长程锚定的地面(证据指针)。

- **记忆是 Script 的投影**（有损、可重建，D 议题）。
- **上下文是记忆(+Script)的投影**（有界切片，R/E 议题）。
- 一切投影最终落回那根**只追加的脊柱** → 这就是"互为投影"不至于变成"互相污染放大"的根据。

**两道守卫成对存在的原因**：因为是闭环，单守一支拦不住雪球——
- **B 守 f 支**：生成忠于记忆（Continuity Critic）。
- **D 守 U 支**：记忆忠于剧本（Faithfulness Check）。
- 两支都夹住，环才稳。（这是"误差投影/拉回合法流形"的微观落地；宏观那端是卷复盘 Replanner。）

**直接推论：R 与 U 必须共设计。** 出库投影 R 的粒度必须匹配入库投影 U 定下的 `S` 表示——
S 存滚动摘要则 R 检索摘要，S 存原文 beat 则 R 检索 beat。**不能先定 R 再回头补 S** —— 这正是
E 的流水桶语义档挂起、要留到"记忆/索引层"里把 `S 表示 + U + R` 当一件事一起设计的原因。

## 6. 与既有架构结论的映射

| 心智模型要素 | 落到 ARCHITECTURE.md 的机制 |
|-------------|---------------------------|
| R（有界上下文） | 分桶检索：走向桶/人设桶/流水桶 + 先过滤后排序 + as-of |
| U（结构化更新） | Recorder：抽取→消解→软失效落库；写回动作集 |
| S 多尺度分量 | 四层存储 ScriptStore/MemoryStore/ArcStore/WorldStore |
| P（全局锚） | L0 立意 → L1 全书结构 → L2 卷大纲 → L3 章 Plan（滚动细化） |
| 误差投影（两支+两尺度） | 微观：B 守 f（Continuity Critic）+ D 守 U（Faithfulness Check）；宏观：卷复盘 Replanner |
| 闭环锚点 | Script spine（主真相），记忆/上下文皆为其投影（§5.5） |
| 外部寻址（长程依赖） | 伏笔台账 + 出处回指（evidence 指针=skip-connection）+ as-of 语义检索 |

## 7. 核心权衡：检索预算（已定框架，见 ARCHITECTURE §8.1）

`R` 的"选多少、选什么"是上下文工程的核心权衡：
- 选少了 → 漂移 / 穿帮 / 伏笔漏收
- 选多了 → 噪声 / 成本 / 冲淡重点

**已定**：分级 MUST/SHOULD/MAY（不平铺 top-k）；长程靠证据锚定（skip-connection）；
lean-by-default, widen-on-error 自适应。
**仍挂起**：流水桶 SHOULD 语义档的具体机制，依赖记忆/索引层设计（检索粒度、滚动摘要、embedding 粒度）。
